# Изменение с проверкой

Цикл «красный тест → минимальная правка → зелёный тест → авторитетный прогон».
Цель — не просто починить, а **доказать**, что дефект был и что он закрыт.

## Вход

Назвать три вещи. Без них не начинать:

1. **Что меняем** — файл и строка.
2. **Какое поведение должно измениться** — наблюдаемое свойство, а не формулировка.
   Например: «при `tool_mode=timeout` итоговый статус перестаёт быть `ok`».
3. **Чем это проверяется** — какой тест или сценарий это увидит.

## Шаги

### 1. Зафиксировать базу

```bash
npm run typecheck && npm test
```

Записать результат. Если база уже красная — сначала чинить её, иначе доказательство
будет неотличимо от шума.

### 2. Написать падающий тест — ДО правки

Тест добавляется в `tests/` и проверяет **свойство**, а не точный текст ответа:
статус, число, аргументы вызова. Свободный текст модели сравнивать нельзя
(`CONTRACT.md:56`).

```bash
npm test
```

Убедиться, что тест падает **по ожидаемой причине**, а не по опечатке или
несуществующему импорту. Прочитать сообщение об ошибке целиком.

### 3. Минимальная правка

Править только то, что названо во входе. Не трогать соседний код, не
переименовывать, не рефакторить заодно. Разрешённые зоны — в `CLAUDE.md`.

### 4. Зелёный на хосте

```bash
npm run typecheck && npm test
```

Оба должны пройти. Если typecheck красный — правка не закончена: этот же
`tsc` стоит гейтом внутри `Dockerfile:7` и уронит сборку образа.

### 5. Авторитетный прогон в контейнере

Код запечён в образ, а не смонтирован, поэтому **пересборка обязательна**:

```bash
docker compose up -d --build --wait
docker compose exec -T agent npm test
docker compose exec -T -e AGENT_URL=http://localhost:8090 agent npm run preflight
uv run python scripts/evaluate.py
```

Либо всё сразу, вместе с линтерами: `./scripts/check.sh`.

Последнюю строку пропускать нельзя, и вот почему. `npm test` проверяет **выход
инструмента**, а `evaluate.py` — **что доходит до пользователя** через полный путь
агента. Это разные уровни: правка может закрыть дефект на уровне инструмента и всё
равно оставить неверный ответ в чате. Дефект адаптера был виден именно так — тест
на статус ловил его, а в ответе пользователь видел «Начислено 0 коп».

Здесь закреплены Node 24.14.0 и версии из `package-lock.json`. Расхождение
между хостом и контейнером — само по себе находка, разбирать, а не игнорировать.

### 6. Сохранить доказательства

Прогоны «до» и «после» сложить в `artifacts/` под разными именами.
`artifacts/runs.jsonl` **не очищать** — разделять прогоны по `run_id`.

## Критерий завершения

Выполнены все пункты, иначе работа не закончена:

- [ ] тест **падал** до правки и **проходит** после — на одном и том же тесте
- [ ] `npm run typecheck` чист
- [ ] `npm test` зелёный на хосте и в контейнере
- [ ] `npm run preflight` — PASS
- [ ] `uv run python scripts/evaluate.py` — все сценарии PASS, код возврата `0`
- [ ] изменены только файлы из разрешённой зоны (`git status` это подтверждает)
- [ ] результаты «до» и «после» лежат в `artifacts/`

## Явный стоп

**Если новый тест зелёный ещё до правки — остановиться и вернуться к шагу 2.**

Такой тест не доказывает ничего: он не отличает исправленный код от сломанного.
Доказательство — один и тот же тест, который падал на дефекте и прошёл после
правки. Зелёный с самого начала так не умеет.

Проверить обратимость: если вернуть дефект, тест обязан снова упасть.
