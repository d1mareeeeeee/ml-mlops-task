# Диагностика по логам

Связывает сценарий, запуск агента, вызовы инструментов и конечный ответ через `run_id`.
Задача — не «починить», а **назвать причину и указать тест**, который её ловит.

Исправление — дело парного skill'а `change-with-verification`. Сначала диагноз,
потом правка: иначе тест проверяет догадку, а не причину.

## Вход

`run_id` прогона, либо `--last` для последнего. `run_id` возвращается в ответе
`POST /run` и записан в каждой строке `artifacts/runs.jsonl`.

## Инструмент

```bash
uv run python scripts/explain_run.py <run_id>
uv run python scripts/explain_run.py --last
```

Коды возврата: `0` — расхождений нет, `1` — есть находки, `2` — прогон не найден.

## Что именно смотреть

Каждое событие содержит **и** `source` (что вернул источник), **и** `result`
(что получил агент) — их кладёт туда `src/tools.ts:27`. Расхождение между ними
и есть прямая улика.

```
  2. get_charges  args={"account_id": "acc-alice", "period": "2026-08"}
     source=timeout  result=ok   <-- РАСХОЖДЕНИЕ
```

Здесь источник отказал, а агенту сообщили об успехе. Дальше модель честно
просуммировала пустой массив и выдала «Начислено 0 коп. Источник успешно прочитан.»
с HTTP 200.

## Классификация

Обязательно отнести сбой к одной из трёх категорий:

| Признак | Категория | Что делать |
|---|---|---|
| `source.status` ≠ `result.status` | **ошибка реализации** | искать в `src/adapter.ts` |
| статусы корректны, данные дошли, но ответ им противоречит | **нарушение поведения модели** | значимо только для `mode=real` |
| HTTP 503 / `BLOCKED`, либо запись с `error` при `mode=real` | **блокировка провайдера** | не FAIL; отметить отдельно |

Полезный дискриминатор: системный промпт `src/agent.ts:6` **уже** содержит
`timeout is not zero`. Если инструкция верна, а ответ неверен — виновата
реализация, а не промпт.

Отдельный случай: `mode=real` без ключа бросает исключение **до** создания
`run_id` (`src/agent.ts:8-10`), поэтому в JSONL такой прогон не попадает вообще.
Блокировку видно только по HTTP 503 от сервера.

## Чего делать нельзя

- Считать HTTP 200 признаком успеха. `CONTRACT.md:35-36` прямо предупреждает:
  дефект даёт неверный результат именно с кодом 200.
- Путать `empty` и `timeout`. `status=ok` с пустым массивом — это успешное
  чтение пустого периода, законный ноль. Инструмент их различает: на `empty`
  он возвращает `0`, на `timeout` с дефектом — `1`.
- Чистить `artifacts/runs.jsonl`. Это доказательства (`README.md:50-51`).

## Критерий завершения

Разбор закончен, когда названы все три вещи:

1. **Где** — конкретный `файл:строка`.
2. **Что подтверждает** — какое свойство контракта нарушено и чем это видно в логе.
3. **Какой тест ловит** — имя существующего теста либо описание теста, который
   нужно добавить.

Без третьего пункта разбор остаётся рассказом: причина названа, но ничто не мешает
ей вернуться.

## Пример завершённого разбора

> **Где:** `src/adapter.ts`, спецслучай для статуса `timeout`.
> **Что подтверждает:** нарушено требование `CONTRACT.md:47` — `timeout` обязан
> оставаться неуспехом. В событии 2 прогона `680136f4` видно `source=timeout`
> при `result=ok`; пользователь получил нулевую сумму как успешно прочитанную.
> **Какой тест ловит:** регрессионный тест на `tool_mode=timeout`, проверяющий
> что итоговый статус не `ok`. Существующие тесты в `tests/contract.test.ts`
> дефект не видят — все три гоняют режим `success`.
