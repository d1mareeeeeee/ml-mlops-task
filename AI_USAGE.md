### Что задано в `CLAUDE.md`

Карта кода с указанием участка изменения, команды сборки и проверок для TypeScript и
Python, границы разрешённого, место хранения результатов и факты контракта (статусы,
суммы, токены сессий) — чтобы агент не выдумывал значения.

Отдельно вынесены три ловушки стенда, на которых легко ошибиться: два порта (8090
внутри контейнера, 8091 снаружи), отсутствие Python в образе и то, что код запекается
в образ через `COPY`, а не монтируется — значит после каждой правки нужна пересборка.

### Что закрыто машинно

`deny` на `fixtures/**`, `package-lock.json`, `uv.lock`, `CONTRACT.md`, `Dockerfile`,
чтение и запись `.env`.

Проверено: запись в `fixtures/data.json` и чтение `.env` отклонены с
`File is in a directory that is denied by your permission settings`.


`allow` на частые безопасные команды (`npm test`, `npm run typecheck`, `git status`,
`docker compose up/exec/ps/logs`, `uv run`) — чтобы не подтверждать каждый вызов.

## Где ещё применялся агент

**Планирование через plan mode.** Перед каждым крупным блоком агент писал план, который
утверждался до правок. Порядок коммитов — инструменты и тесты раньше фикса — тоже
результат планирования: иначе снимок «до» снять нечем, инструмента измерения ещё нет.

**Ревью skill'ов через `skill-creator`.** Изначально skill'ы написаны вручную: структуру
задаёт условие (вход, исполняемая команда, критерий завершения), а они сами узкие и
привязаны к этому репозиторию — ссылаются на конкретные файлы, порты и команды.
Эмпирический цикл `skill-creator` с бенчмарками рассчитан на переиспользуемые skill'ы.

Для контроля оба прогнаны через `skill-creator` в режиме ревью, и это нашло две реальные
проблемы — описаны ниже.

**Разбор работы стенда.** Агент объяснял устройство выданного кода по месту: два порта
(8090 внутри контейнера, 8091 снаружи), что делает `tool_mode` и почему дефект виден
только в ветке `timeout`, как мок-модель выбирает инструменты регулярками, почему
`preflight` остаётся зелёным при дефекте.

## Пример 1. `diagnose-from-logs` на учебном дефекте

### Контекст, который получил агент

- `run_id` прогона, где сценарий S4 дал `FAIL`;
- из `CLAUDE.md` — что `artifacts/runs.jsonl` пишется автоматически из `src/agent.ts`,
  и что HTTP 200 не означает PASS;
- текст скилла

### Команда

```bash
uv run python scripts/explain_run.py 4efce473-0caf-483a-8f56-fdb3dca9d188
```

### Вывод

```
События (2):
  1. get_account  args={"account_number": "10001"}
     source=ok  result=ok
  2. get_charges  args={"account_id": "acc-alice", "period": "2026-08"}
     source=timeout  result=ok   <-- РАСХОЖДЕНИЕ

Ответ агента:
  Счёт 10001, период 2026-08. Начислено 0 коп. Источник успешно прочитан.

Находки:
  [ошибка реализации] Событие 2 (get_charges): источник вернул 'timeout', агенту
  передано 'ok'. Статус подменён по пути. Где смотреть: src/adapter.ts.
```

Проблема - расхождение `source` и `result` в одном событии. Оба поля пишет
`src/tools.ts`: `source` это ответ источника, `result` — то, что ушло агенту. Между
ними стоит адаптер.

### Критерий завершения skill'а

| Пункт | Результат |
|---|---|
| Где | `src/adapter.ts`, спецслучай для статуса `timeout` |
| Что подтверждает | нарушено `CONTRACT.md:47` — `timeout` обязан оставаться неуспехом; ноль выдан как успешно прочитанный при HTTP 200 |
| Какой тест ловит | `timeout stays a failure and never becomes an empty success` в `tests/adapter.test.ts`; существующие тесты стартового комплекта дефект не видят — все три гоняют `tool_mode=success` |

### Как проверен вывод

1. **Чтение кода.** В `src/adapter.ts` действительно стоял `if (result.status ===
   'timeout') return { status: 'ok', data: [] }`.
2. **Прямой запрос к агенту.** `POST /run` с `tool_mode=timeout` вернул
   «Начислено 0 коп. Источник успешно прочитан.» с кодом HTTP 200.
3. **Код возврата инструмента.** `1` при расхождении и `0` на прогоне с
   `tool_mode=empty`, где ноль законный. То есть инструмент различает отказ источника
   и успешное чтение пустого периода.

## Пример 2. `change-with-verification` на том же дефекте

### Контекст, который получил агент

- вход по правилам skill'а: что меняем (`src/adapter.ts`), какое свойство должно
  измениться (при `tool_mode=timeout` итоговый статус перестаёт быть `ok`), чем
  проверяется;
- из `CLAUDE.md` — разрешённые зоны правки и требование сравнивать свойства, а не
  текст ответа модели;
- из skill'а — явный стоп: если новый тест зелёный ещё до правки, работа
  останавливается.

### Команды и порядок

Порядок принципиален: тест пишется **до** правки.

```bash
# 1. база
npm run typecheck && npm test

# 2. падающий тест, до правки
npm test                      # 4 passed, 2 failed

# 3. минимальная правка: удалена одна строка в src/adapter.ts

# 4. зелёный на хосте
npm run typecheck && npm test  # 6 passed

# 5. авторитетный прогон в контейнере
docker compose up -d --build --wait
docker compose exec -T agent npm test
uv run python scripts/evaluate.py
```

Добавлены три теста в `tests/adapter.test.ts` — два регрессионных и один guard.
Проверяются статусы, аргументы и суммы; свободный текст ответа модели, HTTP-коды и
`mockReply` сознательно не проверяются, потому что `CONTRACT.md:56` требует сравнивать
свойства.

### Как проверен вывод

Сообщения падений читаются целиком (т.е. ждем именно AssertionError)

Третий тест — `an empty period stays a successful read` —
зелёный и до, и после правки. Он держит `CONTRACT.md:52`: правка вида «любой ноль
считать ошибкой» закрыла бы регрессию, но сломала бы законный пустой период за
`2026-09`.

**Три состояния кода, все прогоны в контейнере.** Снимки в `artifacts/`:

| Файл | Прогон | Состояние |
|---|---|---|
| `test-before-fix.txt` | 4/6 | дефект на месте, код из `911cba3` |
| `test-after-fix.txt` | 6/6 | фикс, `71fcefc` |
| `test-reverted.txt` | 4/6 | дефект возвращён поверх фикса |


**Обратимость.** Третий снимок закрывает отдельное требование: возврат той же строки
снова ломает ровно те два теста. Т.е. тесты падают из-за
дефекта, а не из-за чего-то постороннего.

**Агентный уровень.** `npm test` проверяет выход инструмента, а не то, что видит
пользователь. Поэтому отдельно снята пара отчётов evaluator'а:

| Отчёт | Коммит | Итог |
|---|---|---|
| `eval-before.json` | `911cba3` | 8 PASS / 1 FAIL — падает S4 |
| `eval-after.json` | `71fcefc` | 9 PASS |



На полном пути агента ответ при `tool_mode=timeout` сменился с «Начислено 0 коп.
Источник успешно прочитан» на «Невозможно получить начисления: timeout».

## Что проверялось вручную, без агента

Агент работает в песочнице и не имеет доступа к docker-сокету, поэтому вся работа с
контейнером шла через разработчика.

**Прогоны в контейнере.** Четыре пересборки образа, `npm test` в трёх состояниях кода,
`./scripts/check.sh` целиком, прогоны evaluator'а.

**Проверка выводов тестов в терминале.** Вывод каждой команды сверялся с ожиданием до
перехода к следующему шагу: падения читались до блока `AssertionError`, чтобы отличить
красный по существу от красного из-за опечатки или битого импорта.

**Проверка полученных артефактов.** Шапки и содержимое снимков и отчётов читались
отдельно. Так нашлась мёртвая ссылка на коммит и рассогласование версий набора между
отчётами — оба случая описаны ниже.

Все коммиты сделаны разработчиком; сообщение к коммиту с артефактами написано своё, не
предложенное агентом.

## Правки решений агента

### Версия набора: номер заменён на хеш файла со сценариями

К требованию «фиксируйте версию набора тестов» агент предложил завести в
`scripts/evaluate.py` рукописную константу `SUITE_VERSION = "1"`.


Вместо константы был сделан SHA-256 файла со сценариями и
проверками. Меняется сам при любой правке, подделать нельзя, проверяется независимо:

```bash
shasum -a 256 scripts/evaluate.py | cut -c1-12
```



### Условный прогон сценариев в `change-with-verification`

В skill'е шаг 5 требовал запускать `scripts/evaluate.py` при **любом** изменении.

Это перебор: описание skill'а охватывает правки в `src/` и в `tests/`, но девять
сценариев проверяют ответ агента — правка, запертая в `tests/` или `scripts/`, повлиять
на него не может. .

Шаг и чек-лист сделаны условными: прогон сценариев нужен, если правка затронула `src/`.

### Убраны ссылки на условие задания внутри skill'ов

Skill'ы ссылались на PDF с заданием — «этого требует PDF стр. 3» и подобное. Skill не
должен зависеть от документа, которого в репозитории быть не должно.

Все ссылки заменены обоснованием по существу. Например вместо «PDF требует показать один
и тот же регрессионный тест» — «доказательство это один и тот же тест, который падал на
дефекте и прошёл после правки; зелёный с самого начала так не умеет».

### Шаг 2 skill'а не объяснял, что смотреть в выводе

Команда `npm test` в шаге «написать падающий тест» читалась как обращение к какому-то
существующему тесту, хотя это запуск всего набора: `npm test` разворачивается в
`tsx --test tests/*.test.ts`, и новый файл подхватывается маской.

Не было сказано и ожидание на этом шаге — новый тест красный, остальные зелёные. Если
краснеет и существующий, это не доказательство дефекта, а поломка рядом.

Добавлено, плюс признак настоящего красного: нужен `AssertionError` с полями `operator`
и `actual`, то есть проверка выполнилась и не сошлась. `Error: Cannot find module` или
`TypeError` означают, что тест упал не дойдя до проверки, и дефект им не доказан.

### Артефакты сняты в контейнере, а не на хосте

Агент предложил снимать отчёты через хостовый сервер (`PORT=8091 npm start`) — быстрее,
не нужна пересборка.

Для артефактов сдачи приоритет другой: у меня на хосте Node 24.18.0, а задание
закрепляет 24.14.0 по digest образа. Отчёт, снятый на другой версии, не подтверждает
воспроизводимость.

Все снимки `npm test` и все три отчёта evaluator'а пересняты через `docker compose`.

### Мёртвая ссылка на коммит в артефакте

В шапку `test-before-fix.txt` агент вписал коммит `d6a15ab`, которого в ветке не
существовало — остаток откаченной истории. Нашёл разработчик при чтении файла.
 Позже было решено убрать код коммита из шапки теста.
