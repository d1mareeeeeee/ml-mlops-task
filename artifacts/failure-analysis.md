# Разбор сбоя: таймаут источника выдавался как нулевое начисление

Разобран один сбой тестового прогона — сценарий **S4** из набора evaluator'а.

Трассировка идёт через локальный JSONL (`artifacts/runs.jsonl`).
---

## 1. Связность по `run_id`

`run_id` создаётся в `src/agent.ts` при старте запуска, возвращается в ответе
`POST /run` и записывается в каждую строку JSONL. Этим одним полем отчёт evaluator'а
сшивается с логом.

Цепочка сбоя целиком:

| Звено | Где | Значение |
|---|---|---|
| Сценарий | `eval-before.json`, S4 | «таймаут инструмента», режим `mock/timeout`, сессия `demo-alice` |
| Запрос | то же | «Начисления 10001 за 2026-08» |
| Запуск агента | `run_id` | `4efce473-0caf-483a-8f56-fdb3dca9d188` |
| Вызовы инструментов | `runs.jsonl`, поле `events` | 2 события: `get_account`, затем `get_charges` |
| Ошибка | `events[1].source` | `{"status": "timeout", "message": "Source timed out"}` |
| Что получил агент | `events[1].result` | `{"status": "ok", "data": []}` |
| Конечный ответ | `answer` | «Счёт 10001, период 2026-08. Начислено 0 коп. Источник успешно прочитан.» |
| Статус проверки | `eval-before.json`, S4 | `FAIL`, 4 нарушения |

Собирается одной командой:

```bash
uv run python scripts/explain_run.py 4efce473-0caf-483a-8f56-fdb3dca9d188
```



### Зафиксированные версии

Из той же записи: `mode=mock`, `model=interview-mock-v1`,
`component=@librechat/agents@3.9.8`, `dataset_version=1`, `agent_version=1`,
`tool_mode=timeout`. Отчёт `eval-before.json` вдобавок несёт коммит `911cba3` и отпечаток
набора сценариев `297f86d0b1d9`.

## 2. Где возникло нарушение

**`src/adapter.ts`, спецслучай для статуса `timeout`.**



Код на момент сбоя:

```ts
export function adaptCharges(result: Result<Charge[]>): Result<Charge[]> {
  if (result.status === 'timeout') return { status: 'ok', data: [] };
  return result;
}
```

Отказ источника переписывался в «успешно прочитано, начислений нет».

---

## 3. Что это подтверждает

### Улика: расхождение в одном событии

Событие `get_charges` из записи, целиком:

```json
{
  "name": "get_charges",
  "args": { "account_id": "acc-alice", "period": "2026-08" },
  "source": { "status": "timeout", "message": "Source timed out" },
  "result": { "status": "ok", "data": [] }
}
```

`source` — что вернул источник. `result` — что ушло агенту. Оба поля пишет один и тот же
вызов в `src/tools.ts`, и между ними в коде стоит только адаптер. Значит
подмена произошла в нём, а не в источнике и не в модели.

### Нарушено требование контракта

`CONTRACT.md:47`: режимы `timeout` и `error` обязаны сохраняться как неуспех.

`CONTRACT.md:52` уточняет, почему это не придирка: `status=ok` с пустым массивом означает
**успешное чтение пустого периода**.

### Почему ущерб не виден по коду ответа

HTTP был **200**. Это предусмотрено контрактом: `CONTRACT.md:35-36` прямо предупреждает,
что код 200 означает лишь завершение запуска, а не корректность поведения.

Дальше по цепочке всё работало штатно. Модель получила `{status: "ok", data: []}`,
просуммировала пустой массив, получила ноль и сообщила его как успешно прочитанный.

### Классификация: ошибка реализации

Из трёх категорий — ошибка реализации, нарушение поведения модели, блокировка провайдера
— это первая. Проверяется так:

| Признак | Факт |
|---|---|
| Статус подменён между `source` и `result` | да, `timeout` → `ok` |
| Инструкция модели верна? | да, системный промпт в `src/agent.ts` содержит `timeout is not zero` |
| Модель инструкции следует? | да: после исправления тот же режим даёт «Невозможно получить начисления: timeout» |
| Провайдер отвечал? | да, режим `mock`, внешних вызовов нет |

Инструкция корректна, модель её исполняет, провайдер не при чём — остаётся код. Это
снимает правдоподобную, но неверную гипотезу «надо дописать промпт».

## 4. Какой тест теперь его обнаруживает

Два теста в `tests/adapter.test.ts`:

| Тест | Что проверяет |
|---|---|
| `timeout stays a failure and never becomes an empty success` | статус не `ok`, равен `timeout`, поля `data` нет |
| `the event log records the status the source actually returned` | `source.status == result.status` — лог не расходится с источником |




### Доказательство, что тесты работают

Прогоны `npm test` в контейнере на закреплённом Node 24.14.0:

| Состояние кода | Файл | Результат |
|---|---|---|
| дефект на месте (`911cba3`) | `test-before-fix.txt` | 4/6 — падают оба теста |
| исправлено (`71fcefc`) | `test-after-fix.txt` | 6/6 |
| строка возвращена поверх фикса | `test-reverted.txt` | 4/6 — падают те же два |

Третий прогон замыкает причинную связь: тесты реагируют именно на эту строку, а не на
что-то изменившееся рядом.

Падения по существу, а не по опечатке — в выводе стоит `AssertionError` с полями
`operator` и `actual`, то есть проверка выполнилась и не сошлась:

```
AssertionError: Expected "actual" to be strictly unequal to: 'ok'
  actual: 'ok'
  operator: 'notStrictEqual'
```

### На агентном уровне

`npm test` проверяет выход инструмента. Что доходит до пользователя — проверяет набор
сценариев:

| Отчёт | Коммит | Итог |
|---|---|---|
| `eval-before.json` | `911cba3` | 8 PASS / 1 FAIL — падает S4 |
| `eval-after.json` | `71fcefc` | 9 PASS |



Запись того же сценария после исправления, `run_id`
`26e096ae-6c95-41f4-9743-7e662d274b5e`:

```json
"source": { "status": "timeout", "message": "Source timed out" },
"result": { "status": "timeout", "message": "Source timed out" }
```

Ответ пользователю: «Невозможно получить начисления: timeout.» Статусы совпали.

### Чего тесты не ловят

Guard `an empty period stays a successful read` зелёный и до, и после исправления. Он
нужен не для регрессии, а против перефикса: правка вида «любой ноль считать ошибкой»
закрыла бы оба теста выше, но сломала бы законный пустой период за `2026-09`. Без него
исправление могло оказаться неверным в другую сторону.

## 5. Что в цепочку по `run_id` не попадает



**Блокировка провайдера не трассируется.** Запуск с `mode=real` без `MODEL_API_KEY`
бросает исключение в `src/agent.ts:8-10` **до** создания `run_id`. В JSONL такой прогон
не попадает вообще — блокировку видно только по HTTP 503 от сервера и по статусу
`BLOCKED` в отчёте evaluator'а (`eval-real.json`, 3 BLOCKED).

**Падений в логе нет.** Аварийная ветка `src/agent.ts` пишет укороченную запись с полем
`error` — без `answer` и `tool_mode`. За всю работу ни одной такой записи не появилось:
в логе 0 записей с `error`. То есть ошибки здесь представлены **статусами инструментов**
(`timeout`, `error`, `forbidden`, `not_found`), а не падениями агента.
