## Пункт 3. Python-evaluator на сценарии

Проверка **агентного уровня**: каждый сценарий это `POST /run`, то есть полный путь
HTTP -> `server.ts` -> `Run` из `@librechat/agents` -> инструменты -> адаптер -> ответ
модели. Блок 2 проверял выход инструмента без сервера; здесь закрывается требование
PDF п.2 «ошибка доходит до агентного сценария».

### Созданные файлы

#### `scripts/evaluate.py` — 9 сценариев, отчёт, коды возврата

| ID | Категория | Режим | Источник требования |
|---|---|---|---|
| S1 | обычный запрос | `success` | PDF стр. 3 |
| S2 | не указан номер счёта | `success` | PDF стр. 3 |
| S3 | успешный ответ без начислений | `success` | PDF стр. 3 |
| S4 | таймаут инструмента | `timeout` | PDF стр. 3 |
| S5 | посторонний счёт | `success` | PDF стр. 3 |
| S6 | свой: ошибка источника | `error` | `CONTRACT.md:47` |
| S7 | свой: инъекция в данных | `injection` | `CONTRACT.md:29` |
| S8 | свой: неизвестный счёт | `success` | `CONTRACT.md:53` |
| S9 | свой: вторая сессия (`demo-bob`) | `success` | `CONTRACT.md:14-17` |

S3 использует период `2026-09`: в фикстурах начислений за него нет, поэтому пустой
период получается естественно, без искусственного режима `empty`.

S9 добавлен отдельно, уже после первого прогона: все остальные сценарии идут под
токеном `demo-alice`, то есть права per-session были проверены только с одной
стороны. Будь они захардкожены под Alice, набор бы этого не заметил. S9 читает счёт
Боба под его собственным токеном и ожидает 990000 коп.; попутно проверяется, что
сумма Алисы в ответ не течёт. Тем же утверждением об изоляции усилен и S1.

Это выводит набор на 9 сценариев при заявленных в PDF 6–8. Решение осознанное:
диапазон задаёт объём работы, а непроверенная вторая сессия — содержательный
пробел, а не украшение. PDF стр. 4 отдельно предупреждает, что объём кода сам по
себе оценку не повышает, поэтому S9 оправдан только тем, что закрывает реальную
дыру в покрытии.

После добавления S9 пара «до/после» переснята целиком, чтобы оба отчёта были на одном
наборе из 9 сценариев, как требует PDF («результаты до и после исправления на одном
наборе»). Сопоставимость подтверждается совпадающим отпечатком набора — см. ниже.

Проверяются статусы, аргументы вызовов, суммы и количество событий — не формулировки
(`CONTRACT.md:56`). Ко всем восьми автоматически применяется общая проверка
`source.status == result.status`: та же улика, что ищет `explain_run.py`.

Одно узкое исключение из запрета на текст: для S4 и S6 проверяется, что код причины
(`timeout` / `error`) присутствует в ответе пользователю. Это требование PDF стр. 3
«причина доступна в логе и в результате проверки», а не сравнение фразы.

**Как фиксируется набор.** PDF требует «Фиксируйте commit, версию модели или мока,
конфигурацию агента и версию набора тестов». Вместо рукописного номера версии в шапку
отчёта идёт **отпечаток** — короткий хеш файла `scripts/evaluate.py`, где живут и
сценарии, и их проверки. Причины: номер надо помнить и поднимать вручную, он ничего не
доказывает, а commit сейчас не пиннит набор, потому что работа не закоммичена. Отпечаток
меняется автоматически при любой правке сценария или логики проверки, поэтому совпадение
отпечатков у двух отчётов — проверяемое доказательство, что набор был один и тот же.
Хешируется файл целиком: ложное срабатывание на переформатировании безвредно, а пропуск
изменённой проверки — нет.

Коды возврата: `0` всё PASS, `1` есть FAIL, `2` есть BLOCKED. HTTP 400 и 500 считаются
FAIL, а не BLOCKED (`CONTRACT.md:63`); BLOCKED — только HTTP 503 и недоступное
соединение, по образцу `sample_run.py:21-24`.

Переиспользование вместо нового кода: `status_of` и `charges_total` импортируются из
`scripts/explain_run.py` — один источник истины для «что такое статус» и «как считать
сумму». Схема вызова взята из `scripts/sample_run.py`. Сценарии описаны списком
dataclass'ов в коде: YAML с мини-языком проверок был бы «новым фреймворком», которого
PDF просит избегать.

#### `tests/test_evaluate.py` — 3 теста на сами функции-проверки

Без сервера и сети, на синтетических записях. Проверяют, что проверка `timeout`

## Пункт 4. Разбор сбоя

`artifacts/failure-analysis.md` — разбор сценария S4 из прогона на дефектном коде.

Трассировка через локальный JSONL, без Langfuse: условие допускает аналог, а локальный
лог заодно снимает вопрос об утечке — наружу ничего не отправляется.

### Связность по `run_id`

`run_id` создаётся в `src/agent.ts`, возвращается в ответе `POST /run` и пишется в каждую
строку JSONL. Этим одним полем отчёт evaluator'а сшивается с логом. Цепочка сбоя:
сценарий S4 в `eval-before.json` → `run_id` `4efce473` → два события в `runs.jsonl` →
`source.status=timeout` против `result.status=ok` → ответ «Начислено 0 коп. Источник
успешно прочитан.»

Парная запись после фикса — `run_id` `26e096ae`, тот же сценарий со статусом PASS и
ответом «Невозможно получить начисления: timeout.»

### Три обязательных пункта разбора

| Пункт | Содержание |
|---|---|
| Где | `src/adapter.ts`, спецслучай для `timeout`; адрес через условие, а не номер строки |
| Что подтверждает | нарушены `CONTRACT.md:47` и `:52`; HTTP 200 это скрывает |
| Какой тест ловит | два теста в `tests/adapter.test.ts`, с доказательством на трёх состояниях кода |

Классификация сделана проверяемой, а не объявленной: таблица из четырёх признаков —
статус подменён, инструкция модели верна, модель ей следует, провайдер не при чём. Отсюда
«ошибка реализации», и заодно снимается правдоподобная гипотеза «надо дописать промпт».

### Названные границы

Блокировка провайдера по `run_id` **не трассируется**: `mode=real` без ключа бросает
исключение до создания `run_id`, в JSONL такой прогон не попадает. Видно только по
HTTP 503.

Падений в логе нет — аварийная ветка `src/agent.ts` ни разу не срабатывала, 0 записей с
полем `error`. Ошибки здесь представлены статусами инструментов, а не падениями агента.

### Секреты

В `runs.jsonl` нет токенов сессий, заголовка `Bearer`, `MODEL_API_KEY` и внутреннего
ключа мока — сверено. Команда для перепроверки приведена в документе.

## Переписан CI под одиночный репозиторий

`.github/workflows/starter.yml` из стартового комплекта был нерабочим: матрица
`[fullstack, ml-mlops, qa-sdet]` с `working-directory: ${{ matrix.task }}` ожидала три
папки заданий рядом, а здесь одно задание в корне. Шаг с проверками фикстур обращался к
сервису `source-mock`, которого в `compose.yaml` нет.

Вдобавок он не запускал ничего из сделанного: ни evaluator, ни `ruff`, ни `ty`, ни
`pytest` — для ml-mlops эти три инструмента стояли в зависимостях и не вызывались.

Переписан: матрица и `working-directory` убраны, остался один job, который вызывает
`./scripts/check.sh`. Один источник истины — проверка, добавленная в скрипт, попадает в
CI без правки workflow. Перед вызовом `uv sync --frozen --group dev`, потому что шаги
4–7 скрипта работают на хосте: в образе нет Python.

Версия `uv` не пинится: `README.md` упоминает 0.11.6, локально 0.12.10, и пинить версию,
на которой не прогоняли, хуже чем не пинить. Воспроизводимость держит `uv.lock`.

## Правки skill'ов после ревью

Оба skill'а прогнаны через `skill-creator` в режиме ревью. Ревью и последующие замечания
дали четыре правки.

**Прогон сценариев добавлен в шаг проверки.** `change-with-verification` устарел
относительно репозитория: в авторитетном прогоне стояли только `npm test` и `preflight`,
а `scripts/evaluate.py` не упоминался. Следуя skill'у буквально, можно было закрыть
изменение, не проверив, что доходит до пользователя.

**Прогон сценариев сделан условным.** Сначала он был добавлен безусловно, но описание
skill'а охватывает правки и в `src/`, и в `tests/`, а девять сценариев проверяют ответ
агента — правка, запертая в `tests/` или `scripts/`, повлиять на него не может.
Безусловное требование вдобавок провоцирует игнорировать шаг целиком. Теперь прогон
нужен, если затронут `src/`.

**Шаг «сначала падающий тест» дополнен ожиданием.** Команда `npm test` читалась как
обращение к существующему тесту, хотя это запуск всего набора по маске
`tests/*.test.ts`. Добавлено, что ожидается — новый тест красный, остальные зелёные — и
как отличить настоящий красный: нужен `AssertionError` с полями `operator` и `actual`, а
`Error: Cannot find module` означает, что тест упал не дойдя до проверки.

**Убраны ссылки на условие задания.** Skill'ы ссылались на страницы PDF; правило,
зависящее от документа, которого в репозитории не будет, перестаёт работать. Все ссылки
заменены обоснованием по существу.

Протухшая ссылка `src/adapter.ts:3` в примере `diagnose-from-logs` после фикса указывала
на другую строку — заменена на описание через условие, потому что номера сдвигаются при
любой правке файла.

Эмпирическая часть `skill-creator` не выполнялась: тестовые промпты, замер срабатывания
и оптимизация описаний остались вне работы.

## Известные ограничения

Фиксирую честно, как требует PDF («Укажите потраченное время, ограничения и что
осталось незавершённым»).

- **Зеркало S5 не покрыто.** S9 закрыл главный пробел: вторая сессия читает свой счёт
  успешно. Но обратный случай — `demo-bob` просит счёт Алисы и получает `forbidden` —
  не проверен. Путь отказа проверен только со стороны Alice (S5).
- **S2 проверяет полтора свойства из двух.** PDF требует «агент запрашивает уточнение
  и не выдумывает идентификатор». «Не выдумывает» проверено строго (0 вызовов
  инструментов, нет пятизначного числа в ответе), а «запрашивает уточнение» — только
  косвенно. Формально пустой ответ дал бы PASS.
- **Инъекция на моке не доказывает стойкость.** `mock-model.ts` поле `note` не читает,
  поэтому S7 проходит по конструкции (`CONTRACT.md:54-55`). Осмысленный результат
  даст только прогон `--real`, который сейчас BLOCKED.
- **Прямые маршруты `/tools/*` не задействованы.** `CONTRACT.md:38-40` предлагает их
  для проверки прав в обход модели; все наши проверки идут через модель.
- **Срабатывание skill'ов не замерялось.** Описания написаны по рекомендациям
  skill-creator, но прогон тестовых запросов «должен сработать / не должен» не
  выполнялся. То, что skill подхватится на нужной формулировке, предполагается, а не
  проверено.
